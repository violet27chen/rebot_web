# 当前深度相机与快递分拣流程分析

本次只读取 USB 描述、现有运行状态及源码，并核对厂商资料；未修改深度采集、对齐、抓取或训练代码，未新建相机采集会话。

## 设备身份与当前输出

本机实际连接 `2bc5:060f ORBBEC Depth Sensor` 与 `2bc5:050f USB 2.0 Camera`，后者描述为 Sonix。现有 OpenNI 返回名称 `Astra`。因此确定应按旧款 Astra / OpenNI 协议分析。USB 组合与 Astra Pro Plus 常见形态相符，但当前通用设备名不足以严格确定子型号，参数不能直接套用项目中历史 Gemini 2 配置。

读取已有 `/api/depth/status`，单次快照为：

| 项目 | 当前结果 |
| --- | --- |
| 深度流 | 活跃，640×480，SDK 协商 30 fps |
| 格式 | uint16，单位 mm |
| RGB 对齐 | `aligned_to_rgb=false` |
| 驱动 | Orbbec OpenNI 2.3，运行库 2.3.0.86-beta6 |
| 设备链路 | USB 2.0，描述速率 480 Mbit/s |
| 整幅有效深度比例 | 约 60.5%，只代表该时刻的整幅图，不代表工作区质量 |
| 帧龄 | 此次约 63 ms，不等同于完整端到端延迟 |
| 彩色预览 | 独立 UVC RGB 节点，由同一视觉进程管理 |

`backend/openni_depth.py` 请求毫米格式、关闭镜像、检查步长并复制原始深度。`backend/depth_manager.py` 同时生成原始 16 位 PNG 和伪彩 JPEG；零值被视作无效深度。显示颜色映射范围 200～4000 mm 只是显示参数，不代表传感器有效测距范围。代码以 0.065 秒间隔限制发布，因而网页/共享服务实际最多约 15 帧每秒，即使传感器模式是 30 fps。

官方 Astra 系列采用红外结构光，适用于室内；典型深度为 640×480@30fps。不同子型号近端量程不同。Astra Pro Plus 规格书列出的量程为 0.6～8 m、1 m 条件下精度 3 mm；这些是该型号的厂商条件值，不能替代当前安装位置和包裹材质下的测量。[Astra 系列产品页](https://www.orbbec.com/products/structured-light-camera/astra-series/)、[Astra Pro Plus 规格书](https://developer-orbbec-oss.oss-cn-shenzhen.aliyuncs.com/library/product_doc/Astra_Pro_Plus_Datasheet_v1.2.pdf)。

官方 SDK 仓库说明旧 OpenNI 协议设备由 SDK v1 兼容，SDK v2 已不再支持这类旧协议；当前可工作的 OpenNI 链路应先保留。[厂商 SDK 兼容说明](https://github.com/orbbec/OrbbecSDK#orbbec-sdk)。

## 可以提供什么

深度图给出深度相机各像素的 Z 值。配合相机内参可反投影为三维点；配合外参可转换到工作区、左臂和右臂坐标系。由此可以估算桌面平面、包裹高度、占据区域、局部平面朝向、边缘和包裹移动量。RGB 图继续提供盒袋外观、条码和语义类别。

| 比赛阶段 | 结合深度的价值 | 仍需要的信息 |
| --- | --- | --- |
| SCAN_WORKSPACE | 桌面分割、包裹三维位置、是否进入双臂共同可达区 | 相机外参、双臂工作区、空洞与遮挡判断 |
| SKILL_PUSH | 高度与轮廓辅助选择推拢接触区；动作后检查目标是否到位 | 受限运动规则、力矩反馈、重规划 |
| CLASSIFY_PRE | 平面度、高度和褶皱辅助 RGB 判盒袋 | RGB 语义；深度形状不能单独保证类别正确 |
| SKILL_FLIP_BOX | 估算箱体可见面朝向、接触高度、翻面前后变化 | 双臂遮挡处理、接触状态与力矩看门狗 |
| SKILL_FLIP_BAG | 观察整体形变和目标移位，辅助判断是否松脱 | 固定臂力矩、RGB 跟踪；薄袋边缘不能只依赖深度 |
| SCAN_BARCODE | 找较平整可见面，辅助判断是否还需平整或翻面 | 扫码仍靠 RGB 的纹理、清晰度与曝光 |
| CLASSIFY_FINAL | 确认推送目标区、障碍高度和包裹离场 | 条码规则、盒袋类别及机器人安全约束 |

优先价值是“让规则知道包裹在哪里、有多高、是否移动到位”，而不是一开始就增加 ACT 网络复杂度。

## 当前不能直接做的事

1. **不能直接拿 RGB 像素索引深度图。** 两个光学中心和视场不同，即使都是 640×480 也不代表像素对应。必须有 RGB/深度内参与相对外参，完成 D2C 或明确的三维投影和遮挡处理。
2. **不能直接把深度 Z 当机器人高度。** 相机可能倾斜；桌面高度应通过相机外参或桌面平面法向计算。
3. **不能从一张普通深度图自动得出可靠的双臂基座间距。** 若两基座或与基座关系已知的标记在共同视野中，标定后可把两中心变换到同一坐标系，再计算中心距；关节 FK 的各自局部原点并不提供这种共同坐标。
4. **不能把伪彩截图当作毫米测量或原始训练数据。** JPEG 色彩图用于观察；数值运算应使用原始 uint16 深度、单位、时间戳和有效性掩码。
5. **不能认为 RGB 录制已经包含深度。** 当前 `rebot_shared` 插件传输 BGR/RGB 三通道帧；三路相机中的“深度相机”名称当前指其 RGB。原始深度没有自动成为 ACT 的输入特征。
6. **不能承诺零延迟或完全无空洞。** 30 fps 本身就有帧间隔，当前还存在发布限频与编码。黑色、透明、反光材质、强红外背景和机械臂遮挡需要单独评估，不能把深度无效值当作桌面或安全空间。

## 在不改代码前先确定的条件

- 确认铭牌子型号、安装高度与包裹最高点，保证最近表面落在实际有效工作距离内。若按 Pro Plus 的 0.6 m 近端量程分析，相机离桌面 0.8 m、包裹高 0.25 m 时，顶部约 0.55 m，可能进入近端盲区；这是几何分析示例，不是当前安装实测。
- 确认深度相机是固定俯视还是腕部。固定相机需相机到工作区外参；腕部相机需相机到末端的手眼标定并使用对应时刻的关节反馈。
- 收集 RGB/深度内参、畸变参数、相互外参和时间关系。不同 RGB 预览相机之间也不能混用标定。
- 先分析空桌面、纸盒、深浅色袋、反光胶带、双臂遮挡条件下的工作区有效像素比例与稳定高度误差。当前单次全图 60.5% 不能作为这些结论。
- 保留已有单视觉进程，由其分发 RGB 与原始深度；不让采集、推理与 Web 各开一套 SDK。
- 若后续加入训练，先独立保存逐帧原始深度、有效掩码、设备/主机时间戳和标定标识。与各技能独立数据集对应，保持动作仍为双臂 14 维。新增深度编码器及训练方案需要单独设计，当前不实施。

建议推进顺序：型号与工作距离确认 → 工作区深度质量分析 → RGB-D 对齐与外参 → 规则工作区判断和动作后反馈 → 再考虑深度进入 ACT。
